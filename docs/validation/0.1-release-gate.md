# Akira Knowledge 0.1.x 发布就绪验收证据

本文只记录 `0.1.x` Source Spec（GitHub Issue #17）与自动化黑盒证据之间的对应关系，不重新定义产品合同。产品语义仍以 `CONTEXT.md`、accepted ADR、`docs/roadmap/0x-series.md` 与 Source Spec 为准。

## Canonical 黑盒接缝

当前 canonical 行为验收入口是：

```bash
./scripts/check.sh
```

它从 `akira-knowledge` 的共享用户执行入口在隔离临时 Obsidian Vault 中运行黑盒测试，并检查最终 Markdown、Properties、stable identity、revision、provenance、检索结果与 fail-closed 行为。测试不以内部 SQL、函数调用顺序或类结构作为主要验收对象。

## 0.1.x 实现选择说明

`0.1.x` 的 Property Filter 直接读取当前 Markdown Authority 与材料结构化状态，不维护独立的 property Projection。因此不存在需要恢复的 property Projection；相关验收由 `test_filter_supports_kind_material_status_and_user_authority_property` 证明过滤不依赖第二份属性真相。

Full-text Search 使用 SQLite FTS5 作为可重建 Projection。其丢失或损坏不会改变 Markdown Authority，也不会推进 Authority revision。

`knowledge-retrieve` 始终保持 Authority 只读。rename / move / direct edit 的 revision 登记由 `knowledge-maintain` 的同步 / 写入准备负责；纯 move 可以被机械证明与正文替换互不相交，正文变化则使旧 proposal fail closed。

## 最终门禁

发布就绪门禁通过需要同时满足：

- `./scripts/check.sh` 全部通过；
- Python 编译检查通过；
- `git diff --check` 通过；
- Guard 提交 / 架构门禁通过；
- GitHub Issue #24 的全部 Acceptance Criteria 有上述自动化证据；
- 工作树不存在来源不明或未提交的实现修改。

通过本门禁只表示 `0.1.x` 实现满足 Source Spec 的发布就绪条件，不等于已经完成 GitHub tag / release 或远端安装发布。
