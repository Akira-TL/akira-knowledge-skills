# Human-readable Knowledge Writing Contract

本文件定义 Akira Knowledge 对长期人类可读 Knowledge Asset 的正文要求。它约束 `knowledge-curate` 形成 create / update proposal 时的写作质量，也约束 Maintenance 在修改既有正文时不得把知识退化成聊天记录、模型分析稿或不可检索的长文。

## 1. 写作目标

Knowledge Asset 是未来会被人再次查阅、搜索、链接和维护的参考文档，不是：

- 对话记录；
- Agent 的思考过程；
- 一次性报告；
- 材料摘要堆叠；
- 为了显得完整而生成的长篇说明。

正文首先服务未来检索，其次服务连续阅读。读者打开文档后，应在很短时间内知道：

1. 这篇解决什么问题；
2. 核心结论、定义或方法是什么；
3. 什么时候适用；
4. 有什么边界、例外或待核验点；
5. 下一步应该跳到哪些相关知识。

## 2. 知识单元边界

一篇 Knowledge Asset 围绕一个稳定检索目标或一个高内聚知识单元组织。

不要机械追求“一句话一篇”或“一条 Claim 一篇”。过宽会让标题失去指向性、链接变模糊；过碎会破坏上下文与阅读连续性。

拆分信号：

- 标题无法准确代表全文；
- 文档同时回答多个彼此独立的问题；
- 某个小节可以独立被搜索、链接和维护；
- 修改一个部分经常与其他部分无关；
- 正文需要大量“另一个方面”“另外一个问题”才能维持结构。

合并信号：

- 两篇单独打开都缺少必要上下文；
- 两篇总是一起修改和引用；
- 拆开后只能靠来回跳转才能完成一个简单理解任务。

## 3. 标题、文件名与 aliases

标题承担第一检索入口，作用类似稳定的人类“接口”。

- 标题必须具体、可搜索，并能代表正文边界。
- 优先使用人未来真的会搜索的术语、对象名、方法名或问题表达。
- 方法文档优先写清任务，例如“QIIME 2 单端 16S ASV 分析流程”。
- 概念或判断可以使用完整短语，例如“群落同质化 LRR 指标”。
- 避免“笔记”“一些问题”“总结”“相关内容”“资料”“其他”“分析”等无法区分内容的泛化标题。
- 稳定 Knowledge Asset 的文件名应尽量与正式标题一致；路径变化不改变 stable identity。
- 旧名、缩写、英文名、常用拼写与历史名称放入 `aliases`，不要为了兼容旧搜索保留含糊文件名。
- 同一概念始终使用同一术语。缩写首次出现时给出完整名称；后文使用稳定简称。

## 4. 开头直接给答案

一级标题后直接进入定义、结论、用途、适用边界或问题本身。

默认前 1–3 句应让读者判断“这是不是我要找的内容”。不要先写无信息量的铺垫，例如：

- “本文将介绍……”
- “下面我们首先……”
- “在这一部分中……”
- “从整体上来说……”
- “需要明确的是……”——如果后面的内容可以直接陈述，就直接陈述。
- “值得注意的是……”——如果内容重要，就直接写内容本身。

不要在开头复述标题后再解释“为什么要写这篇笔记”，除非来源背景本身影响知识适用性。

## 5. 段落

一个段落表达一个完整意思，并把最重要的信息放在前面。

默认：

- 普通说明段以 2–5 句为宜；
- 一句话段落可以使用，但应是有意强调、定义或边界，不应连续大量出现；
- 6 句以上时检查是否混入多个意思；
- 长段落如果包含多个条件、例外或结论，应拆段或改为结构化列表 / 表格；
- 不为了“短”把一个连续论证切成大量碎片段落。

禁止典型 AI 排版：

> 一个短句。
>
> 又一个短句。
>
> 再解释一句。
>
> 最后再说一遍。

也禁止整屏只有一个巨型段落。

## 6. 句子

句子优先短、完整、直接，但不能碎片化。

- 一句承担一个主要判断、动作或因果关系。
- 条件、适用范围和限制尽量靠近被限制的结论。
- 中文普通句超过约 60–80 字时主动检查是否可以拆分；这是 review 信号，不是机械字符上限。
- 连续多层“由于……因此……同时……而且……从而……”通常应拆句。
- 删除不增加语义的副词、套话和重复限定。
- 不要用多个近义句重复同一个结论。
- 专业术语可以复杂，句法不必复杂。

## 7. 标题层级

标题用于扫描和定位，不用于装饰。

- 每篇 Knowledge Asset 恰好一个 `#` 一级标题。
- 标题层级连续，不从 `##` 跳到 `####`。
- 普通知识优先控制在 `# / ## / ###` 三层。
- 小节标题要能独立说明“这里能找到什么”。
- 优先使用“适用场景”“输入与输出”“参数选择”“失败条件”“与 X 的区别”“验证方法”等检索型标题。
- 避免大量“背景”“概述”“分析”“说明”“进一步说明”“总结”等泛化标题；只有该词本身准确描述内容职责时才使用。
- 不为了编号而写“一、二、三、四”；顺序已经可以由 Markdown 层级和列表表达。

## 8. 列表与表格

列表只表示真正并列或有顺序的信息。

适合列表：

- 条件；
- 参数；
- 步骤；
- 候选项；
- 优缺点；
- 检查清单；
- 明确的并列事实。

不适合把连续解释拆成几十条 bullet。

列表项保持语法并列；同一列表不要混用名词短语、完整句、问题和长段落。需要解释时可以在列表后补正常段落，或把多属性比较改成表格。

表格适合结构化比较，不适合塞长篇叙述。表格单元格如果开始出现多段正文，通常应改回小节。

## 9. 链接与检索

普通 wikilink 服务人类导航，不自动成为 typed relation。

- 在第一次真正相关的位置链接到已有知识。
- 链接文本要能独立说明目标，必要时使用 alias。
- 不给每个专业名词都加链接。
- 不通过堆叠十几个“相关链接”代替正文中的自然连接。
- 一个事实或方法在 owning Knowledge Asset 完整维护；其他文档引用它，避免复制整段形成多份 Authority。
- 如果相关内容有明确的前置、替代、冲突等机器语义，仍走 Relation Candidate 治理，不把写作链接当作机器关系。

## 10. 事实、建议、构想与不确定性

流畅措辞不能掩盖证据状态。

- 已核验事实直接陈述，并保留必要 Source / provenance。
- 方法建议要写适用条件和失败条件。
- 待核验内容明确使用 `review`、`unreviewed`、`partial`、`needs-update` 或正文中的等价表述。
- 构想要区分“当前已知”“假设”“需要验证”“停止条件”。
- 不把模型推测写成事实。
- 不用“可能”“大概”“通常”连续堆叠来制造模糊安全感；不确定时说明具体不确定在哪里。

## 11. 禁止保留 AI 生成痕迹

长期 Knowledge Asset 不保留生成过程或聊天口吻。应删除无知识价值的元话语，例如：

- “我认为……”
- “你可以看到……”
- “我们接下来……”
- “这里需要注意的是……”
- “不难发现……”
- “从上述分析可以看出……”
- “综上所述……”后再次重复全文；
- “首先 / 其次 / 再次 / 最后”仅用于制造形式而非真实顺序；
- 同一个观点换三种说法反复强调；
- 为了显得完整而生成“背景—意义—分析—总结”固定四段式。

知识库保存结论、依据、边界和可复用方法，不保存 Agent 的思考轨迹。

## 12. 不同知识类型的默认结构

这些是按需选择的骨架，不是模板填空。没有内容的小节不要创建。

### 方法 / workflow

优先考虑：

- 解决什么问题；
- 什么时候使用 / 不使用；
- 输入与前置条件；
- 关键步骤或决策点；
- 参数选择；
- 如何验证输出；
- 常见失败模式；
- 替代方案；
- 相关知识。

### 概念 / reference

优先考虑：

- 一句话定义或核心回答；
- 关键机制 / 组成；
- 适用范围；
- 易混淆概念；
- 例外与边界；
- 示例；
- 相关知识。

### idea / review

优先考虑：

- 核心构想或研究问题；
- 当前证据；
- 尚未确认的假设；
- 验证方案；
- 成本和依赖；
- 失败 / 停止条件；
- 与已有知识的关系。

### 比较类知识

优先使用小型表格明确比较维度，再用段落解释真正影响决策的差异。不要用两个长列表让读者自己对齐。

## 13. Curate 提案前自检

在把 proposal 写入 proposal store 前，主模型必须检查：

- 标题是否能作为未来搜索词和链接句柄；
- 打开前 30 秒能否知道这篇解决什么；
- 是否存在无信息量开场；
- 是否有重复语义可以删除；
- 是否连续出现多个单句段；
- 是否有墙状长段落；
- 是否有超长、多层嵌套句；
- 列表是否真的并列；
- 标题是否具体并且层级连续；
- 是否残留对话、报告或 AI 元话语；
- 事实、建议、待核验内容是否区分；
- 是否应该链接既有知识而不是复制；
- 文档是否过宽需要拆分，或过碎需要合并。

如果任一项明显失败，先重写 proposal，再持久化候选。

## 14. 确定性检查器的边界

工具可以确定性发现结构异常，例如：

- 缺少或存在多个一级标题；
- 标题层级跳跃；
- 连续大量单句段；
- 明显墙状段落；
- 明显 AI 元话语；
- 过度列表化；
- 泛化标题。

这些检查只是写作 review 辅助，不判断科研真伪、语义是否完整，也不以固定字符数代替主模型判断。硬结构错误可以 fail closed；风格 finding 必须由 Curate 主模型结合正文判断并在 proposal 前解决。

## 15. 设计依据

本合同吸收但不照搬以下公开实践：

- Andy Matuschak 的 Evergreen Notes：知识应面向概念、高内聚、可持续演化，标题承担类似 API 的稳定句柄；atomicity 需要在可复用和上下文完整之间权衡。
- Zettelkasten 社区实践：长期笔记应形成自己的表达、可独立理解，并通过链接进入知识网络。
- Dendron：文件名应使用未来检索时会想到的词；层级保持足够简单，内容真正变大后再拆分。
- Obsidian：Markdown、Properties、aliases、内部链接和搜索共同承担本地可读与可找回能力。
- Google Developer Documentation Style Guide：描述性标题、层级连续、一个段落一个意思、重要信息前置，避免墙状文本。
- Microsoft Writing Style Guide：先给重点，句子和段落保持简洁，列表保持并列结构，内容应便于扫描。
- PARA / Progressive Summarization：组织和摘要的目标是未来可找回、可使用，而不是为了分类本身增加维护成本。

Akira Knowledge 不采用任何单一外部方法作为产品模型。上述实践只用于校准人类阅读、检索与维护习惯；Authority、identity、revision、Relation 与 lifecycle 仍由 Akira Knowledge 自己定义。
